M1 edge AI: fleet, mower runtime and a GD32 proof of concept

The M1 display runs the mower runtime, adds an on-device AI layer that turns J1939 signals (and optionally sound and camera images) into health scores and events, and syncs them to a fleet manager. The proof of concept uses GigaDevice's GD32 Embedded AI tool to quantize and deploy models on a GD32H759 Cortex-M7.

Bottom line

Start the proof of concept with the model that fits the data the display already has: an LSTM health model on J1939 time series (engine and hydraulic temperatures, oil pressure, fuel rate, load). It needs no new hardware, runs comfortably on a Cortex-M7, and has a built-in benchmark: the self-learning anomaly baseline already in the AI Terra mower firmware. Sound and camera models come second, because they need a microphone or the M1's camera input and more memory.

The GD32H759 gives a second silicon source with three CAN-FD channels. The main open question is integration: the tool generates Keil and IAR projects, while the M1 SDK builds with STM32CubeIDE and GCC.

Proof of concept with the GD32 tool: eight weeks

WK 1–2 Data and baseline

  • GD32H759 evaluation board with CAN-FD transceiver; replay recorded mower J1939 logs
  • Export labelled 60 s windows (normal / abnormal) as NPZ
  • Run the existing anomaly baseline on the same logs

EXIT Dataset and baseline scores agreed

WK 3–4 Train and quantize M1

  • Train a small LSTM; export H5 or ONNX
  • GD32 tool: analysis, int8 quantization with NPZ calibration, benchmark report
  • Compare two or three model sizes

EXIT int8 model within budget, accuracy loss under 2 points

WK 5–6 Run on target

  • Generated Keil or IAR project runs on the board
  • Feed live replayed CAN through the J1939 stack and data layer
  • Show score and events on a test screen

EXIT End-to-end on hardware, measured latency and memory

WK 7–8 Fleet loop and decision

  • Log events and model version; sync to a phone and a mock fleet manager
  • Signed model update into a second slot, with rollback
  • Decide: port into the M1 build, and STM32 vs GD32

Fleet manager loop

Up: machine to fleet

  1. The display computes scores and events on the machine
  2. Events, scores, model version and engine hours go into the log ring
  3. Phone app syncs the log over BLE (M1v / M1iv)
  4. Fleet manager shows health per machine and schedules service
  5. Confirmed faults become labels for retraining

Down: fleet to machine

  1. A new model is trained, quantized with the GD32 tool and tested
  2. The model package is signed and listed in the SBOM
  3. The fleet manager targets units by model and firmware version
  4. Phone app delivers it over BLE to the model manager
  5. The display checks the signature, loads it into the spare slot and rolls back if self-tests fail
