# M1 display SDK: working guide for Claude Code

This file tells Claude Code how to work safely and efficiently in a maximatecc M1 display project. It applies to any machine or application built on a M1 display. It contains no application-specific requirements; put those in your own project notes.

## How to use this file

- Put this file in the root of your M1 project.
- Claude Code automatically reads `CLAUDE.md`. Either rename this file to `CLAUDE.md`, or add this line to your existing `CLAUDE.md`:

  ```
  @maximatecc_for_claude.md
  ```

- Fill in every item marked **VERIFY** (collected in the last section) against your SDK release before relying on this guide. Until then, Claude must treat those items as unknown and ask rather than assume.
- Keep application specifics (machine type, signal list, screen designs, customer requirements) in a separate file such as `PROJECT.md`, and import it the same way.
- The file has two parts. **Part 1** is the working rules for any M1 project. **Part 2** describes the long-term partnership maximatecc wants with Wainbee and the toolkit built for it. Claude treats Part 2 as context and templates; where Part 2 and Part 1 seem to disagree, Part 1 wins.

# Part 1: Working rules for any M1 project

## SDK architecture and ownership

The 280 SDK is layered. Each layer has an owner. Claude works only in the layers marked "Claude may edit".

| Layer | Contents | Claude may edit? |
|---|---|---|
| Application | Customer logic, screen flow, unit conversions for display | Yes |
| GUI | TouchGFX (MVP pattern) **or** Qt for MCUs (QML subset compiled to C++) | Yes, in the non-generated parts (see GUI rules) |
| Data layer | `GET_DL` / `SET_DL` access by field id; field ids defined in `database.h` | Yes: add and document fields. Do not change the access mechanism |
| Platform services | FreeRTOS tasks, J1939 and CANopen stacks | Configuration only, through the SDK configuration interface. No changes to stack internals |
| MCAL | Generated by STM32CubeMX: GPIO, timers, ADC, communication peripherals | **No.** The SDK manual says the MCAL should not be altered |
| Bootloader, linker script, startup code | Flash layout and reset behaviour | **No** |

### Data flow (one direction for reading, one for commands)

```
CAN bus / inputs ─► platform services (J1939, CANopen, I/O) ─► SET_DL(field)
                                                                  │
                                              data layer (database.h fields)
                                                                  │
GUI (TouchGFX Model::tick or Qt for MCUs backend) ◄─ GET_DL(field) ┘
GUI commands (key presses, settings) ─► SET_DL(command field) ─► application / platform services
```

The GUI never talks to CAN, HAL or MCAL directly. Everything crosses the data layer.

## What Claude must not change

1. **MCAL and generated driver code.** Do not edit files produced by STM32CubeMX outside their `/* USER CODE BEGIN */ … /* USER CODE END */` blocks, and do not regenerate the CubeMX project unless an engineer asks. Ask maximatecc support for MCAL changes.
2. **Bootloader, linker script, startup file, flash layout.**
3. **CAN stack internals.** Configure J1939 and CANopen only through the provided configuration. A proprietary message set or object dictionary beyond the defaults may need maximatecc's tailored CAN library. Say so instead of writing a parallel stack.
4. **Licensed components.** Do not copy, modify or redistribute Qt for MCUs or TouchGFX library code. Do not change licence files or headers.
5. **Generated GUI code.** TouchGFX files under `generated/`, and code generated from QML by the Qt for MCUs tools, are overwritten on every generation. Edit the designer project or the hand-written sources instead.
6. **Safety-relevant behaviour.** Do not add, remove or change warnings, telltales, interlocks or anything the machine's risk assessment treats as safety-relevant, unless a named engineer explicitly asks in the current task. When a change touches such behaviour, stop and say so.
7. **Secrets and customer data.** Never write keys, passwords or customer-confidential data into source files, commit messages or logs.

## Data-layer rules

- Read machine data in the GUI only with `GET_DL(<field id>)`. Write commands and settings only with `SET_DL(<field id>, <value>)`. Exact signatures and return types: **VERIFY** in your SDK headers before use.
- Field ids live in `database.h`. When adding a field:
  1. Add the id next to related fields, using the existing naming style.
  2. Document it in a comment: source (PGN/SPN, CANopen index/subindex, or input pin), unit, scaling, valid range, and what "not available" looks like.
  3. Store values in engineering units with a stated resolution (for example `°C × 1`, `km/h × 10`, `% × 2`). Do not store raw CAN bytes for the GUI to decode.
  4. Set the field from exactly one producer (one decoder or one input handler).
- **Stale and invalid data must look different from real data.** J1939 reserves the top of each range (8-bit `0xFB–0xFF`, 16-bit `0xFB00–0xFFFF`, 32-bit `0xFB000000–0xFFFFFFFF`) for error and not-available. Never show those as numbers. If the SDK provides a validity or timestamp mechanism, use it (**VERIFY**). Otherwise ask before inventing one. The GUI shows `--` for a value that is invalid or older than about three broadcast periods.
- Never read a data-layer field in an interrupt handler unless the SDK documents it as ISR-safe (**VERIFY**).

## CAN rules

### J1939

- Use SAE J1939-71 scaling exactly: resolution, offset and byte position per SPN. When unsure of an SPN's definition, ask for the J1939 Digital Annex entry or the OEM's DBC. Never guess scaling.
- Byte positions in J1939 documents are 1-based; C arrays are 0-based. Write both in the comment, for example `/* SPN 110, byte 1 → data[0] */`.
- Multi-byte values are little-endian (Intel byte order).
- Diagnostic messages: DM1 (PGN 65226) carries active faults; DM2 (PGN 65227) previously active. DTC layout: SPN in 19 bits, FMI in 5 bits, occurrence count in 7 bits. Lamp status is in the first two bytes.
- Some PGNs are sent only on request (for example engine hours, PGN 65253). Check how the SDK issues requests (**VERIFY**) before assuming a value arrives by itself.
- Proprietary PGNs (Proprietary A 61184 / 0xEF00, Proprietary B 65280–65535) mean whatever the OEM's DBC says. Take layout and scaling only from that DBC or a written specification, never from a guess or a similar-looking machine.

Common standard PGNs, for reference:

| PGN | Name | Typical content |
|---|---|---|
| 61444 (0xF004) | EEC1 | Engine speed (SPN 190, 0.125 rpm/bit) |
| 61443 (0xF003) | EEC2 | Engine load at current speed (SPN 92) |
| 65262 (0xFEEE) | ET1 | Engine coolant temperature (SPN 110, 1 °C/bit, −40 °C offset) |
| 65263 (0xFEEF) | EFL/P1 | Engine oil pressure (SPN 100, 4 kPa/bit) |
| 65266 (0xFEF2) | LFE1 | Fuel rate (SPN 183, 0.05 L/h per bit) |
| 65276 (0xFEFC) | DD1 | Fuel level (SPN 96, 0.4 %/bit) |
| 65253 (0xFEE5) | HOURS | Engine total hours (SPN 247, 0.05 h/bit), on request |
| 65271 (0xFEF7) | VEP1 | Battery potential (SPN 168, 0.05 V/bit) |
| 65265 (0xFEF1) | CCVS1 | Wheel-based vehicle speed (SPN 84, 1/256 km/h per bit) |
| 65226 (0xFECA) | DM1 | Active diagnostic trouble codes |

### CANopen

- Follow CiA 301. Map objects by index and subindex from the device's EDS file or written specification. Never assume an object's meaning from its index alone.
- Respect the node's NMT state. Do not read process data as valid before the node is operational.

## GUI rules

### Shared (both SDK variants)

- The ST-SDK (TouchGFX) and the Qt-SDK (Qt for MCUs) are **separate, incompatible builds**. Work only in the variant the project uses. Do not mix files or tools between them.
- Keep screen logic thin: format and display values from the data layer, send commands through the data layer, nothing else.
- Use integer or fixed-point values for display formatting. Avoid `printf` of floats unless the project already does.
- Design for the real screen: 240 × 320 on the 280, 480 × 272 on the 430. Use large, high-contrast text for values read at a glance, and remember the keys: these displays are operated with 4 buttons, often with gloves.
- Every value that can be unavailable needs a defined "not available" appearance.

### TouchGFX (ST-SDK, TouchGFX 4.25)

- Follow the Model–View–Presenter pattern the SDK uses. `Model::tick()` reads the data layer and notifies presenters. Presenters pass values to views. Views only draw.
- Change widgets and screens in TouchGFX Designer, then write behaviour in the hand-written classes under `gui/src` and `gui/include`. Never edit `generated/`.
- Call `invalidate()` only on widgets whose content changed, to keep frame time low.
- Text needing runtime values uses wildcard buffers sized for the longest string, including the unit.

### Qt for MCUs (Qt-SDK, Qt for MCUs 2.11)

- Qt for MCUs is commercial-only. Confirm the project has a valid licence before suggesting this path.
- Use the QML subset Qt for MCUs supports. No arbitrary JavaScript, no dynamic object creation at runtime unless the documentation allows it.
- Expose data-layer values to QML through a C++ interface (a singleton with properties, fed through an event queue from the producing task). Keep bindings simple: one property, one purpose.
- Keep image and font sizes within the flash budget. Check the generated resource sizes after each change.

## Real-time and memory rules

- FreeRTOS: never block in the GUI task. No waits on queues with long timeouts, no busy loops, no `HAL_Delay` in GUI code.
- Task rates and priorities are set through the SDK configuration interface. Change them there, not by editing task creation code (**VERIFY** where that interface lives).
- No dynamic allocation (`malloc`, `new`) after start-up in GUI or data-layer code unless the project already does it and explains why.
- Stay within the memory budget. After every build, report the change in flash and RAM use against the previous build (from the build output or `arm-none-eabi-size` on the `.elf`). Flag any change larger than 5 % of free space.
- Interrupt handlers stay short: copy data and signal a task. No decoding, no formatting, no data-layer writes unless the SDK says they are ISR-safe.

## Build, flash and test

Required tools, per the 280 SDK manual:

| Tool | Version | Used by |
|---|---|---|
| STM32CubeIDE | 1.18.1 | Both variants |
| GNU Tools for STM32 | 13.3.rel1 | ST-SDK |
| Arm GNU Toolchain | 12.3.rel1 (registered as `arm_gcc_12.3.1`) | Qt-SDK |
| STM32CubeMX + STM32H7 HAL | 6.14.1 | Both |
| STM32CubeProgrammer | 2.19.0 or later | Both |
| ST-LINK Utility | 2.1.1-2 | Both |
| TouchGFX | 4.25 | ST-SDK |
| Qt for MCUs | 2.11.1 | Qt-SDK |

Do not upgrade any tool version without an engineer's agreement. The SDK is validated against these.

### Building

- The normal build is in STM32CubeIDE. For a command-line build (for Claude Code or CI), STM32CubeIDE has a headless mode. Typical form (**VERIFY** paths and project name):

  ```
  stm32cubeide --launcher.suppressErrors -nosplash \
    -application org.eclipse.cdt.managedbuilder.core.headlessbuild \
    -data <workspace-dir> -build <project-name>/<Debug|Release>
  ```

- A build must finish with no new warnings. Treat new warnings as failures.

### Flashing

- Flash with STM32CubeProgrammer over SWD (ST-LINK). Typical form (**VERIFY** the file name and any external-flash loader the project needs for assets):

  ```
  STM32_Programmer_CLI -c port=SWD -w <build-output>.elf -v -rst
  ```

- Claude must not flash hardware unless an engineer asks in the current task and confirms a unit is connected.

### Testing on the PC

The SDK does not ship a simulator or host test framework. Until it does:

- Put CAN decoding, scaling and formatting in plain C functions that don't include HAL or FreeRTOS headers, so they compile and run on a PC with `gcc`.
- For every decoder, write a host test with real example frames: one normal value, one boundary value, and the "error" and "not available" codes.
- Keep host tests in a `tests/` folder with a `Makefile` or `CMakeLists.txt` that builds them without the STM32 toolchain.
- On hardware, verify with a recorded CAN log or a CAN interface replaying known frames.

## How Claude should work in this project

1. **Restate the request** as a short plan: which data-layer fields, which decoder, which screens, which tests. Then make the change.
2. **Keep diffs small.** One signal or one screen change per task unless asked otherwise.
3. **Ask instead of assuming** when any of these is missing: signal scaling or byte position, the meaning of a proprietary PGN or CANopen object, whether something is safety-relevant, or which SDK variant the project uses.
4. **After each change, report:**
   - files changed and why
   - build result and new warnings, if any
   - flash and RAM change
   - tests added and their results
   - anything left for an engineer to check on hardware
5. **Never claim hardware behaviour you have not seen.** Say "builds and passes host tests" rather than "works on the display" unless an engineer reports it running.
6. **Commit messages** describe the machine-visible change, for example `ui: show coolant temperature on main screen (ET1, SPN 110)`. Follow the project's own convention if it has one.

### Definition of done

- [ ] Build passes in the project's SDK variant with no new warnings
- [ ] Every new data-layer field is documented (source, unit, scaling, range, not-available)
- [ ] Every new decoder has host tests, including the error and not-available codes
- [ ] Unavailable or stale values look different on screen
- [ ] Flash and RAM change reported and within budget
- [ ] No changes to MCAL, bootloader, generated code, licensed code or safety behaviour
- [ ] An engineer has reviewed the diff before merge

# Part 2: maximatecc × Wainbee long-term partnership

This part is written from Wainbee's side: what its product manager and its engineering team in Quebec are trying to get done, and how M1 plus Claude Code can help them win more projects, faster. Everything here is a **proposal** from maximatecc. Items need agreement from both companies before they become commitments.

None of this is tied to one machine type. Wainbee serves many industries (mobile hydraulics, automation, mining, forestry, construction and more), so every feature below is meant to work across different OEM customers and machines.

## Who we are designing for

**The product manager** owns Wainbee's display and controls offer for OEM customers. Goals:

- Win OEM projects against other distributors and integrators
- Quote quickly and accurately, then deliver on that quote
- Reuse engineering work across customers to protect margin
- Keep customers for the life of their machines, through service and updates
- Show OEMs something different from the CrossControl and other lines Wainbee also carries: M1 as the fastest display to customise with AI

**The engineering team** builds and supports the displays. Goals:

- Get from a customer's first meeting to a working screen in days, not weeks
- Juggle several OEM projects at once without mixing them up
- Work in French and English, with customers who expect French
- Support machines in remote places (mines, forests, northern sites) without travelling for every issue
- Avoid rework: catch CAN, layout and memory problems on the PC before hardware

## Features

### 1. 48-hour demo kit

From an OEM's DBC file (or a PGN/SPN list) and a photo or sketch of their current gauges, produce a working demo on a M1 280 within two working days.

- Claude reads the signal list, proposes three screen layouts sized for 240 × 320, and builds the chosen one using Part 1 rules
- Signals without a real source in the demo are fed from a recorded or synthetic CAN log, clearly marked "DEMO DATA" on screen
- Output: a flashable build, a short video of the screen, and a one-page summary in French and English

### 2. Quote helper

Turn a customer's signal list and screen sketches into an effort estimate and a draft statement of work.

- Counts signals by type (standard J1939, proprietary, CANopen, analog input), screens and special features (diagnostics, camera, Bluetooth)
- Applies Wainbee's own effort rates, kept in `wainbee/rates.md` (Wainbee fills this in; maximatecc never sees it unless shared)
- Lists the open questions to ask the customer before committing
- Output: estimate table plus statement-of-work draft, for an engineer to check

### 3. Wainbee screen catalogue

A library of reusable, tested building blocks owned by Wainbee:

- Gauges and bar indicators sized for the 280 and M1
- Active-fault list (DM1) with SPN/FMI lookup text
- Service-interval reminder and hour meter
- Settings screen (units, language, brightness)
- About screen (software version, serial number, customer contact)
- Each block comes with host tests, a screenshot and a short description in `wainbee/catalogue/`
- Customer branding (colours, logo, fonts) goes in a small theme file per customer, so blocks restyle without code changes

### 4. Customer variants from one codebase

One shared code base, with a thin layer per OEM:

```
common/                 shared catalogue blocks, decoders, tests
customers/<oem-a>/      PROJECT.md, theme, signal map, screens unique to this OEM
customers/<oem-b>/      ...
```

- Claude works on one customer folder at a time and says which one at the start of each task
- A fix in `common/` triggers the host tests of every customer variant before merge

### 5. Bilingual by default: français et English

- Every user-visible string lives in a string table with `fr-CA` and `en-CA` entries; no text is written directly in screen code
- Claude maintains a Quebec French glossary of machine terms in `wainbee/glossaire-fr-CA.md` (for example *température du liquide de refroidissement*, *pression d'huile moteur*, *heures moteur*) so wording stays consistent across customers
- French text often runs longer than English. Claude checks that the longest translation fits on screen and proposes abbreviations a Quebec operator would recognise when it doesn't
- Manuals, test records and release notes are produced in both languages
- Quebec's Charter of the French Language sets requirements for French on products and their documentation. Confirm the exact obligations for each product with qualified counsel (**VERIFY**); Claude does not give legal advice

### 6. Cold-climate design kit

The M1 280 and M1 are specified for operation from −20 °C (storage from −30 °C). Quebec winters regularly go colder, and machines may sit outside overnight.

- Raise this with maximatecc for each project: extended-temperature variant, cab installation, or a warm-up strategy (**VERIFY** options with maximatecc)
- Screen design for cold: LCD response slows in the cold, so avoid fast animations and thin moving needles; prefer large digits and solid bars
- Show a clear warm-up or "display warming" state if the application needs it
- Large targets and key-based navigation for gloved hands
- Include cold-start behaviour in acceptance tests where the customer's machines will be outdoors

### 7. Field-support pack

Help Wainbee support machines far from the office:

- **Service screen** behind a key combination: software version, serial number, CAN bus load, last value and age for each key signal, active faults
- **QR code on the service screen** encoding version, serial number and active fault codes. A technician scans it with a phone and Wainbee's support desk gets the facts without a long call. (Use a small MIT-licensed QR library; check flash cost first.)
- **On M1v / M1iv:** use Bluetooth to pull logs to a phone (**VERIFY** what the Bluetooth link supports today)
- Customer-specific troubleshooting notes stored in the customer folder, so Claude can help a Wainbee engineer diagnose a ticket from the QR data

### 8. CAN replay and regression tests

- Record real CAN traffic from each customer's machine (with permission) using a standard CAN interface and its logging tool
- Replay those recordings in host tests, so every change is checked against real data from that customer's machines
- Build up a regression suite per customer over time. This becomes a lasting asset: future changes are safer and faster

### 9. Acceptance-test generator

- From `PROJECT.md` and the screen list, Claude drafts a factory acceptance test: each signal, its source, test value, expected display and pass/fail box
- Bilingual, formatted for the OEM's quality team to sign
- Engineers run it on the bench; results are filed in the customer folder

### 10. Requirements from meeting notes

- Paste meeting notes, in French or English. Claude turns them into a `PROJECT.md` draft: signals, screens, limits, languages, environment, and a list of open questions
- Supports the design-thinking "define" step without extra paperwork

### 11. Per-customer isolation

Wainbee holds confidential CAN databases from several OEMs. Protect them in tooling as well as process:

- Prefer one repository per OEM customer. When a shared repository is unavoidable, use Claude Code permission rules so a session cannot read other customers' folders. Example `.claude/settings.json` in `customers/<oem-a>/`:

  ```json
  {
    "permissions": {
      "deny": [
        "Read(../<oem-b>/**)",
        "Read(../<oem-c>/**)"
      ]
    }
  }
  ```

- Never paste one customer's signals, screens or notes into another customer's task
- Wainbee chooses its own Claude plan and data settings; confirm they meet each OEM's confidentiality terms (**VERIFY** per contract)
